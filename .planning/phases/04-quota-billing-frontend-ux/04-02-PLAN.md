# Phase 4 Plan 02: Privacy Consent and Generation History APIs

## Must Haves

- Block the first generation until the privacy agreement has been accepted.
- Persist agreement state so the user is not forced to re-accept every launch.
- Provide a paginated generation history API for the "My Works" view.
- Reuse existing generation job data and signed result URLs instead of duplicating result storage.

## Tasks

<task id="04-02-01">
  <objective>Add a user-scoped privacy consent record and API pair for checking and accepting the agreement.</objective>
  <read_first>
  - `python-bff/app/api/v1/auth.py`
  - `python-bff/app/api/deps.py`
  - `python-bff/app/models/user.py`
  - `python-bff/app/models/tenant.py`
  - `python-bff/app/schemas/auth.py`
  </read_first>
  <action>
  Add a `user_consents` table and `UserConsent` model with fields `id`, `tenant_id`, `user_id`, `consent_type`, `consented_at`, `source`, and `metadata_json`.

  Add `GET /api/v1/privacy/agreement-status` and `POST /api/v1/privacy/accept`:
  - `agreement-status` returns whether the current user has accepted the generation privacy agreement
  - `accept` stores the current timestamp and the agreement source `generation`

  Also surface the consent status on `GET /api/v1/auth/me` so the frontend can bootstrap its gate without a second round trip.
  </action>
  <acceptance_criteria>
  - `python-bff/app/api/v1/privacy.py` contains `agreement-status` and `accept`
  - `python-bff/app/models/user_consent.py` defines `class UserConsent`
  - `GET /api/v1/auth/me` returns a consent-related field such as `privacy_accepted_at` or `has_privacy_agreement`
  - `python-bff/tests/test_privacy_api.py` exits 0
  </acceptance_criteria>
</task>
